# 16. 팀 규모로 AI를 쓸 때 보강할 것

AI가 코드를 빨리 만들수록 병목은 코드 작성에서 다른 곳으로 옮겨 갑니다. 이 문서는 그 다음 병목 네 가지와,
레포 성격(프로토타입/운영)에 따라 사람 리뷰를 어디에 둘지를 다룹니다.
설계와 중복 작업은 [14](14-design-first-and-overlap.md), 하네스 다이어트는 [15](15-lean-harness.md)에 있습니다.

## 1. 리뷰 병목

AI 도입 후 PR 수와 크기가 늘고 리뷰 대기가 길어집니다(Faros AI 2026: 리뷰 체류 +441%). 리뷰 시간은 늘릴 수
없으니 **들어오는 양을 조절하고, 리뷰어가 볼 곳을 알려 주는** 쪽으로 갑니다.

| 장치 | 위치 | 동작 |
| --- | --- | --- |
| 1인당 리뷰 대기 PR 상한 | `pr-checks.yml`의 `review-load` | 초안이 아닌 열린 PR이 상한(변수 `MAX_OPEN_PRS_PER_AUTHOR`, 기본 3)을 넘으면 알림. 막지 않음 |
| Reviewer guide | PR 템플릿 | "먼저 볼 곳 / 내가 확인한 것 / 확인 못 한 것". AI 생성 PR에서 비어 있으면 알림 |
| 응답 목표 | 팀 합의 | 첫 리뷰 응답 1영업일. 늦어지는 PR은 주간 보드 리뷰(15분)에서 다룸 |

## 2. 계약 먼저

여러 레포 협업에서 가장 비싼 사고는 같은 파일 충돌이 아니라 **API·이벤트·스키마가 조용히 깨지는 것**입니다.

1. T2 설계 템플릿의 **"3-1. 계약 변화"**에 대상·호환성·소비자를 적고, `areas`에 `contract:<이름>`을 넣어 겹침 확인에 걸리게 합니다.
2. 계약 파일은 `contracts/`(또는 `openapi*.yaml`, `*.proto`, `*.schema.json`)에 두고, **계약 PR이 구현보다 먼저** 머지됩니다.
3. `contract-check.yml`이 계약 파일이 바뀐 PR에 댓글을 달고, OpenAPI(oasdiff)와 protobuf(buf, `buf.yaml`이 있을 때)는
   깨지는 변경을 자동 탐지합니다. 깨지는 변경은 `breaking-change` 라벨(소비자와 전환 계획 합의)이 있어야 통과합니다.

## 3. 같은 지적이 두 번 나오면 규칙으로

리뷰에서 같은 말을 반복하는 것은 사람의 시간을 가장 낭비하는 일입니다.

- `scripts/ai/review-comments.sh`가 지난주 PR 리뷰 댓글을 모으고(결정적, 토큰 0), 주간 유지보수 리포트(`make ai-maintenance`,
  `claude-maintenance.yml`)가 이를 주제별로 묶어 **2개 이상의 PR에서 나온 주제마다 고칠 방법 하나**를 제안합니다.
- 우선순위: ① 린트 규칙이나 테스트(결정적) → ② `AGENTS.md`/`.claude/rules/` 한 줄. 문장 규칙은 마지막 수단입니다([15](15-lean-harness.md)).
- 제안은 이슈로만 올라오고, 반영은 사람이 PR로 합니다.

## 4. 스킬 품질 관리

팀 플러그인의 스킬은 모든 팀원의 AI 동작을 바꿉니다. 프롬프트도 코드처럼 테스트합니다.

- `plugins/team-ai-workflow/evals/`에 스킬별 평가 케이스가 있습니다. 케이스 = 사용자 요청(`prompt.md`) + 채점기(`graders/*.md`:
  스킬 호출 여부 `tool_used`, 결과 판정 `llm`).
- **양쪽을 다 봅니다**: 써야 할 때 쓰는가(`design-for-cross-area-work`), 쓰지 말아야 할 때 안 쓰는가(`no-design-for-typo`).
  규칙이 과하면 사소한 일에도 절차를 강요하므로 부정 케이스가 중요합니다.
- 실행: `make ai-eval`(본인 `claude` 로그인, 키 불필요, 케이스당 몇 센트). `make ai-validate`는 평가가 없는 스킬을 경고합니다.
- 이 레포에서 실제로 평가가 잡아낸 것: `/design` 스킬이 "팀을 위해 시작해 줘" 같은 요청에서 호출되지 않는 경우가 있어 설명문을 고쳤고,
  고친 뒤 3/3 통과, 오타 수정에는 여전히 0/3 호출을 확인했습니다.

**개인 스킬 → 팀 스킬 승격 절차**

1. 개인 `~/.claude/skills/` 또는 레포 `.claude/skills/`에서 2주 이상 써 본다.
2. 플러그인으로 옮기는 PR에 **긍정 1 + 부정 1** 평가 케이스를 함께 넣는다. 설명문(description)이 호출을 결정하므로 거기에 공을 들인다.
3. `plugin.json`과 `marketplace.json` 버전을 함께 올린다. 팀원은 `claude plugin update`로 받는다.
4. 분기마다 잘 안 쓰이거나 모델 기본 동작과 겹치는 스킬은 지운다([15](15-lean-harness.md) §4).

## 5. 프로토타입과 운영: 사람 리뷰를 어디에 둘까

### 코드 자체를 보는 일은 사라질까?

컴파일러의 링킹 결과를 아무도 리뷰하지 않는 이유는 **결정적이고, 명세가 정확하고, 수십 년의 테스트가 쌓여 있어서**입니다.
LLM 코드 생성은 아직 셋 다 아닙니다. 같은 요청에 다른 코드가 나오고, 명세는 자연어라 모호하며, 틀리는 방식도 예측하기 어렵습니다.

그래서 리뷰는 사라지기보다 **위로 이동**하고 있습니다.

| 예전에 사람이 본 것 | 옮겨 가는 곳 |
| --- | --- |
| 코드 한 줄 한 줄 | 의도: 설계·계약(이 레포의 T2 설계, 계약 변화 절) |
| "이 코드가 맞나?" | 검증: 수용 기준을 담은 테스트, 계약 diff, 평가(eval), 미리보기 배포 |
| 모든 PR | 위험 기반 표본: 보안 경계, 데이터·스키마 마이그레이션, 결제·권한, 동시성 |

코드는 여전히 **사고가 났을 때 읽어야 하는 기록**이고, 공급망·프롬프트 인젝션으로 들어온 백도어를 잡는 마지막 장소입니다.
그래서 운영 서비스에서는 "모든 줄을 읽는 리뷰"는 줄어도 "위험한 곳을 읽는 리뷰"는 남는다고 봅니다.
프로토타입에서는 이미 사람 리뷰가 거의 없다는 관찰이 맞고, 그게 합리적입니다. 대신 프로토타입이 운영으로 넘어가는 순간을 놓치지 않는 것이 중요합니다.

### 레포 프로필

| | `prototype` | `production`(기본) |
| --- | --- | --- |
| 적용 | `make github-setup PROFILE=prototype` | `make github-setup` |
| PR 필수, squash, force-push·삭제 금지 | 유지 | 유지 |
| CI(`ci-ok`) 필수 | 유지 | 유지 |
| 사람 승인 · CODEOWNER · 에이전트 승인 게이트 | **없음** | 1명 이상 |
| 리뷰 대기 상한 알림 | 끔(변수 `REVIEW_PROFILE=prototype`) | 켬 |
| 비밀·보호 경로 훅, 설계 겹침 확인, 계약 검사 | 유지 | 유지 |

결정적 안전장치(비밀, 히스토리 보호, CI)는 프로필과 상관없이 남깁니다. 사람만 빠집니다.

### 운영으로 넘어가는 조건

다음 중 하나라도 해당하면 `PROFILE=production`으로 바꾸고, 그 시점의 코드에 대해 **한 번의 전체 리뷰**(위험 구간 중심)를 합니다.

- 실제 사용자나 실제 데이터(개인정보, 결제)가 들어온다
- 다른 레포·팀이 이 레포의 API나 이벤트에 의존하기 시작한다(계약이 생긴다)
- 장애가 나면 누군가 호출된다(on-call)
- 비밀이나 운영 인프라 권한을 갖게 된다
