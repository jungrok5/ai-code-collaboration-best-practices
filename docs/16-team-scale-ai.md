# 16. 팀 규모로 AI를 쓸 때 보강할 것

AI가 코드를 빠르게 생성할수록 병목은 코드 작성에서 다른 단계로 이동합니다. 이 문서는 그다음에 나타나는 병목 네
가지와, 레포 성격(프로토타입/운영)에 따라 사람 리뷰를 어디에 둘지를 다룹니다.
설계와 중복 작업은 [14](14-design-first-and-overlap.md), 하네스 축소는 [15](15-lean-harness.md)에서 다룹니다.

## 1. 리뷰 병목

AI 도입 후 PR의 수와 크기가 늘고 리뷰 대기 시간이 길어집니다(Faros AI 2026: 리뷰 체류 +441%). 리뷰 시간은
늘릴 수 없으므로 유입되는 양을 조절하고 리뷰어가 먼저 볼 위치를 명시합니다.

| 장치 | 위치 | 동작 |
| --- | --- | --- |
| 1인당 리뷰 대기 PR 상한 | `pr-checks.yml`의 `review-load` | 초안이 아닌 열린 PR이 상한(변수 `MAX_OPEN_PRS_PER_AUTHOR`, 기본 3)을 넘으면 알림. 차단하지 않음 |
| Reviewer guide | PR 템플릿 | "먼저 볼 곳 / 내가 확인한 것 / 확인 못 한 것". AI 생성 PR에서 비어 있으면 알림 |
| 응답 목표 | 팀 합의 | 첫 리뷰 응답 1영업일. 지연된 PR은 주간 보드 리뷰(15분)에서 처리 |

## 2. 계약 먼저

여러 레포가 협업할 때 가장 비용이 큰 사고는 같은 파일의 충돌이 아니라 API·이벤트·스키마가 알림 없이 깨지는
경우입니다.

1. T2 설계 템플릿의 "3-1. 계약 변화"에 대상·호환성·소비자를 기재하고 `areas`에 `contract:<이름>`을 넣어 겹침 확인 대상에 포함합니다.
2. 계약 파일은 `contracts/`(또는 `openapi*.yaml`, `*.proto`, `*.schema.json`)에 두고, 계약 PR을 구현 PR보다 먼저 머지합니다.
3. `contract-check.yml`이 계약 파일이 바뀐 PR에 댓글을 작성합니다. OpenAPI(oasdiff)와 protobuf(buf, `buf.yaml`이 있을 때)는
   깨지는 변경을 자동으로 탐지합니다. 깨지는 변경은 `breaking-change` 라벨(소비자와 전환 계획 합의)이 있어야 통과합니다.

## 3. 같은 지적이 두 번 나오면 규칙으로

리뷰에서 같은 지적이 반복될 때 사람의 시간이 가장 많이 소모됩니다.

- `scripts/ai/review-comments.sh`가 지난주 PR 리뷰 댓글을 수집하고(결정적, 토큰 0), 주간 유지보수 리포트(`make ai-maintenance`,
  `claude-maintenance.yml`)가 이를 주제별로 묶어 2개 이상의 PR에서 나온 주제마다 수정 방법을 하나씩 제안합니다.
- 우선순위: ① 린트 규칙이나 테스트(결정적) → ② `AGENTS.md`/`.claude/rules/` 한 줄. 문장 규칙은 마지막 수단입니다([15](15-lean-harness.md)).
- 제안은 이슈로만 등록되며 반영은 사람이 PR로 합니다.

## 4. 스킬 품질 관리

팀 플러그인의 스킬은 모든 팀원의 AI 동작을 바꿉니다. 따라서 프롬프트도 코드처럼 테스트합니다.

- `plugins/team-ai-workflow/evals/`에 스킬별 평가 케이스가 있습니다. 케이스 = 사용자 요청(`prompt.md`) + 채점기(`graders/*.md`:
  스킬 호출 여부 `tool_used`, 결과 판정 `llm`).
- 양방향을 모두 확인합니다. 필요할 때 호출하는지(`design-for-cross-area-work`), 불필요할 때 호출하지 않는지(`no-design-for-typo`).
  규칙이 과하면 사소한 작업에도 절차를 강요하므로 부정 케이스를 반드시 포함합니다.
- 실행: `make ai-eval`(본인 `claude` 로그인, 키 불필요, 케이스당 몇 센트). `make ai-validate`는 평가가 없는 스킬에 경고를 표시합니다.
- 이 레포에서 평가로 실제 발견한 사례: `/design` 스킬이 "팀을 위해 시작해 줘" 같은 요청에서 호출되지 않는 경우가 있어 설명문을 수정했습니다.
  수정 후 3/3 통과했고, 오타 수정 요청에서는 여전히 0/3 호출임을 확인했습니다.

### 개인 스킬을 팀 스킬로 올리는 절차

1. 개인 `~/.claude/skills/` 또는 레포 `.claude/skills/`에서 2주 이상 사용합니다.
2. 플러그인으로 옮기는 PR에 긍정 1개, 부정 1개의 평가 케이스를 함께 넣습니다. 설명문(description)이 호출 여부를 결정하므로 설명문을 신중하게 작성합니다.
3. `plugin.json`과 `marketplace.json`의 버전을 함께 올립니다. 팀원은 `claude plugin update`로 받습니다.
4. 분기마다 사용 빈도가 낮거나 모델 기본 동작과 겹치는 스킬을 삭제합니다([15](15-lean-harness.md) §4).

## 5. 프로토타입과 운영: 사람 리뷰의 위치

### 코드를 직접 보는 리뷰는 사라지는가

컴파일러의 링킹 결과는 결정적이고 명세가 정확하며 수십 년의 테스트가 쌓여 있어서 아무도 리뷰하지 않습니다.
LLM 코드 생성은 아직 세 조건을 모두 충족하지 못합니다. 같은 요청에 다른 코드가 생성되고 명세는 자연어라 모호하며 오류 양상도 예측하기 어렵습니다.

따라서 리뷰는 사라지기보다 상위 단계로 이동하고 있습니다.

| 예전에 사람이 본 것 | 이동하는 위치 |
| --- | --- |
| 코드 한 줄 한 줄 | 의도: 설계·계약(이 레포의 T2 설계, 계약 변화 절) |
| "이 코드가 맞나?" | 검증: 수용 기준을 담은 테스트, 계약 diff, 평가(eval), 미리보기 배포 |
| 모든 PR | 위험 기반 표본: 보안 경계, 데이터·스키마 마이그레이션, 결제·권한, 동시성 |

코드는 여전히 사고가 발생했을 때 읽어야 하는 기록입니다. 공급망·프롬프트 인젝션으로 유입된 백도어를 발견하는 마지막 지점이기도 합니다.
따라서 운영 서비스에서는 모든 줄을 읽는 리뷰는 줄더라도 위험 구간을 읽는 리뷰는 남는다고 판단합니다.
프로토타입에서는 이미 사람 리뷰가 거의 없다는 관찰은 사실이며 그 방식도 합리적입니다. 다만 프로토타입이 운영으로 전환되는 시점을 놓치지 않아야 합니다.

### 레포 프로필

| | `prototype` | `production`(기본) |
| --- | --- | --- |
| 적용 | `make github-setup PROFILE=prototype` | `make github-setup` |
| PR 필수, squash, force-push·삭제 금지 | 유지 | 유지 |
| CI(`ci-ok`) 필수 | 유지 | 유지 |
| 사람 승인 · CODEOWNER · 에이전트 승인 게이트 | **없음** | 1명 이상 |
| 리뷰 대기 상한 알림 | 끔(변수 `REVIEW_PROFILE=prototype`) | 켬 |
| 비밀·보호 경로 훅, 설계 겹침 확인, 계약 검사 | 유지 | 유지 |

결정적 안전장치(비밀, 히스토리 보호, CI)는 프로필과 관계없이 유지되며 사람 승인만 제외됩니다.

### 운영으로 전환하는 조건

다음 중 하나라도 해당하면 `PROFILE=production`으로 변경하고 그 시점의 코드를 위험 구간 중심으로 한 차례 전체 리뷰합니다.

- 실제 사용자나 실제 데이터(개인정보, 결제) 유입
- 다른 레포·팀이 이 레포의 API나 이벤트에 의존하기 시작함(계약 발생)
- 장애 시 담당자 호출(on-call) 발생
- 비밀이나 운영 인프라 권한 보유
