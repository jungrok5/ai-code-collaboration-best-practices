# 16. 팀 규모로 AI를 쓸 때 보강할 것

AI가 코드를 빨리 만들수록 병목은 코드 작성에서 다른 곳으로 옮겨 가요. 이 문서는 그다음 병목 네 가지와
레포 성격(프로토타입/운영)에 따라 사람 리뷰를 어디에 둘지 다뤄요.
설계와 중복 작업은 [14](14-design-first-and-overlap.md), 하네스 다이어트는 [15](15-lean-harness.md)에 있어요.

## 1. 리뷰 병목

AI 도입 후 PR 수와 크기가 늘고 리뷰 대기가 길어져요(Faros AI 2026: 리뷰 체류 +441%). 리뷰 시간은 늘릴 수
없으니 들어오는 양을 조절하고 리뷰어가 볼 곳을 알려 줘요.

| 장치 | 위치 | 동작 |
| --- | --- | --- |
| 1인당 리뷰 대기 PR 상한 | `pr-checks.yml`의 `review-load` | 초안이 아닌 열린 PR이 상한(변수 `MAX_OPEN_PRS_PER_AUTHOR`, 기본 3)을 넘으면 알림. 막지 않음 |
| Reviewer guide | PR 템플릿 | "먼저 볼 곳 / 내가 확인한 것 / 확인 못 한 것". AI 생성 PR에서 비어 있으면 알림 |
| 응답 목표 | 팀 합의 | 첫 리뷰 응답 1영업일. 늦어지는 PR은 주간 보드 리뷰(15분)에서 다룸 |

## 2. 계약 먼저

여러 레포가 협업할 때 가장 비싼 사고는 같은 파일 충돌이 아니라 API·이벤트·스키마가 조용히 깨지는 거예요.

1. T2 설계 템플릿의 "3-1. 계약 변화"에 대상·호환성·소비자를 적고, `areas`에 `contract:<이름>`을 넣어 겹침 확인에 걸리게 해요.
2. 계약 파일은 `contracts/`(또는 `openapi*.yaml`, `*.proto`, `*.schema.json`)에 두고, 계약 PR을 구현보다 먼저 머지해요.
3. `contract-check.yml`이 계약 파일이 바뀐 PR에 댓글을 달아요. OpenAPI(oasdiff)와 protobuf(buf, `buf.yaml`이 있을 때)는
   깨지는 변경을 자동으로 찾아요. 깨지는 변경은 `breaking-change` 라벨(소비자와 전환 계획 합의)이 있어야 통과해요.

## 3. 같은 지적이 두 번 나오면 규칙으로

리뷰에서 같은 말을 반복하면 사람의 시간이 가장 많이 새요.

- `scripts/ai/review-comments.sh`가 지난주 PR 리뷰 댓글을 모으고(결정적, 토큰 0), 주간 유지보수 리포트(`make ai-maintenance`,
  `claude-maintenance.yml`)가 이를 주제별로 묶어 2개 이상의 PR에서 나온 주제마다 고칠 방법을 하나씩 제안해요.
- 우선순위: ① 린트 규칙이나 테스트(결정적) → ② `AGENTS.md`/`.claude/rules/` 한 줄. 문장 규칙은 마지막 수단이에요([15](15-lean-harness.md)).
- 제안은 이슈로만 올라오고 반영은 사람이 PR로 해요.

## 4. 스킬 품질 관리

팀 플러그인의 스킬은 모든 팀원의 AI 동작을 바꿔요. 그래서 프롬프트도 코드처럼 테스트해요.

- `plugins/team-ai-workflow/evals/`에 스킬별 평가 케이스가 있어요. 케이스 = 사용자 요청(`prompt.md`) + 채점기(`graders/*.md`:
  스킬 호출 여부 `tool_used`, 결과 판정 `llm`).
- 양쪽을 다 봐요. 써야 할 때 쓰는지(`design-for-cross-area-work`), 쓰지 말아야 할 때 안 쓰는지(`no-design-for-typo`).
  규칙이 과하면 사소한 일에도 절차를 강요하니 부정 케이스를 꼭 넣어요.
- 실행: `make ai-eval`(본인 `claude` 로그인, 키 불필요, 케이스당 몇 센트). `make ai-validate`는 평가가 없는 스킬을 경고해요.
- 이 레포에서 평가가 실제로 잡아낸 것: `/design` 스킬이 "팀을 위해 시작해 줘" 같은 요청에서 호출되지 않는 경우가 있어 설명문을 고쳤어요.
  고친 뒤 3/3 통과했고, 오타 수정에는 여전히 0/3 호출인 것을 확인했어요.

### 개인 스킬을 팀 스킬로 올리는 절차

1. 개인 `~/.claude/skills/` 또는 레포 `.claude/skills/`에서 2주 이상 써 봐요.
2. 플러그인으로 옮기는 PR에 긍정 1개, 부정 1개 평가 케이스를 함께 넣어요. 설명문(description)이 호출을 결정하니 설명문을 공들여 써요.
3. `plugin.json`과 `marketplace.json` 버전을 함께 올려요. 팀원은 `claude plugin update`로 받아요.
4. 분기마다 잘 안 쓰이거나 모델 기본 동작과 겹치는 스킬은 지워요([15](15-lean-harness.md) §4).

## 5. 프로토타입과 운영: 사람 리뷰를 어디에 둘까

### 코드 자체를 보는 일은 사라질까?

컴파일러의 링킹 결과를 아무도 리뷰하지 않는 이유는 결정적이고, 명세가 정확하고, 수십 년의 테스트가 쌓여 있어서예요.
LLM 코드 생성은 아직 셋 다 아니에요. 같은 요청에 다른 코드가 나오고, 명세는 자연어라 모호하고, 틀리는 방식도 예측하기 어려워요.

그래서 리뷰는 사라지기보다 위로 옮겨 가고 있어요.

| 예전에 사람이 본 것 | 옮겨 가는 곳 |
| --- | --- |
| 코드 한 줄 한 줄 | 의도: 설계·계약(이 레포의 T2 설계, 계약 변화 절) |
| "이 코드가 맞나?" | 검증: 수용 기준을 담은 테스트, 계약 diff, 평가(eval), 미리보기 배포 |
| 모든 PR | 위험 기반 표본: 보안 경계, 데이터·스키마 마이그레이션, 결제·권한, 동시성 |

코드는 여전히 사고가 났을 때 읽어야 하는 기록이에요. 공급망·프롬프트 인젝션으로 들어온 백도어를 잡는 마지막 장소이기도 해요.
그래서 운영 서비스에서는 "모든 줄을 읽는 리뷰"는 줄어도 "위험한 곳을 읽는 리뷰"는 남는다고 봐요.
프로토타입에는 이미 사람 리뷰가 거의 없다는 관찰은 맞고 그게 합리적이에요. 대신 프로토타입이 운영으로 넘어가는 순간을 놓치지 마세요.

### 레포 프로필

| | `prototype` | `production`(기본) |
| --- | --- | --- |
| 적용 | `make github-setup PROFILE=prototype` | `make github-setup` |
| PR 필수, squash, force-push·삭제 금지 | 유지 | 유지 |
| CI(`ci-ok`) 필수 | 유지 | 유지 |
| 사람 승인 · CODEOWNER · 에이전트 승인 게이트 | **없음** | 1명 이상 |
| 리뷰 대기 상한 알림 | 끔(변수 `REVIEW_PROFILE=prototype`) | 켬 |
| 비밀·보호 경로 훅, 설계 겹침 확인, 계약 검사 | 유지 | 유지 |

결정적 안전장치(비밀, 히스토리 보호, CI)는 프로필과 상관없이 남기고 사람 승인만 빠져요.

### 운영으로 넘어가는 조건

다음 중 하나라도 해당하면 `PROFILE=production`으로 바꾸고, 그 시점의 코드를 위험 구간 중심으로 한 번 전체 리뷰해요.

- 실제 사용자나 실제 데이터(개인정보, 결제)가 들어옴
- 다른 레포·팀이 이 레포의 API나 이벤트에 의존하기 시작함(계약이 생김)
- 장애가 나면 누군가 호출됨(on-call)
- 비밀이나 운영 인프라 권한을 갖게 됨
